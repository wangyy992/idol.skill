# PRD：从 Dear U bubble 获取聊天记录（可行性研究）

> 状态：**研究阶段（Discovery）** — 目标不是先实现，而是先让 code 把三个关键前置问题查清楚，再决定走哪条技术路线。
> 适用对象：本人订阅账号下、本人可见的聊天记录导出（个人数据可携带 / 个人备份用途）。
> 平台：Dear U bubble（디어유 버블，SM 系 K-pop 偶像私信订阅服务，韩国公司 DearU Co., Ltd.）。

---

## 1. 背景与目标

### 1.1 核心问题（One-liner）
**把「自己账号里能看到的 bubble 聊天记录」完整、结构化地导出到本地**，用于个人存档 / 二次处理（翻译、检索、时间线整理等）。

### 1.2 为什么难
- bubble 的私信内容**以 App 为主要载体**，没有明显的「读消息」网页端。
- 官方**没有公开的一键导出**功能。
- App 侧存在**截图防护**（2021-06 上线过截图禁用更新），是否影响 iOS 待确认。

### 1.3 成功标准（Definition of Done for Discovery）
不是写代码，而是对下面三个问题给出**可执行的、有证据支撑的结论**，每个问题标注：
- ✅ 可行 / ⚠️ 有条件可行 / ❌ 不可行
- 证据（官方页面 / 抓包 / 实机验证）
- 若可行，最小验证脚本 / 步骤

## 2. 候选路线（等待研究结论后收敛）

| 代号 | 路线 | 前置条件 | 合规性 | 稳定性 |
|------|------|----------|--------|--------|
| **A** | 官方个人数据查阅/导出请求（PIPA/GDPR） | 官方有导出入口且导出内容包含消息正文 | ✅ 最高 | 慢，一次性 |

## 3. 给 code 研究的三个关键问题 ★

> 下面每个问题都附了**本轮初步调研结论**（来源见第 6 节）。code 的任务是**验证/证伪并补齐实机证据**，不要停留在二手结论。

### 问题 1 —「Bubble 有没有网页版？」（决定路线 C 成不成立）
**为什么关键**：有可读消息的网页版 → Playwright 自动化是最优解（DOM 结构稳定、可分页翻历史、无截图防护）。

**初步结论：⚠️ 目前只找到「Web STORE」，没找到「读消息的网页端」。**
- 已确认存在网页：`store.dearu.com` / `ba-web-store.dear-u.co` —— 但功能是**买订阅券 / 兑换码 / 礼品**，不是收发/查看私信。
- 未找到任何「在浏览器里读 bubble 聊天」的官方入口或社区记录；消息收取与历史查看均指向 **App 内**。

**code 需要验证**：
1. 登录 `store.dearu.com` 后，除了商店，是否有任何「消息 / inbox / 聊天」页面（查站点地图、登录后重定向、前端路由 `/message` `/chat` `/inbox` 等）。
2. App 抓包时，消息接口是否为**纯 REST/GraphQL + JSON**（若是，则 Web 化的技术前提存在，即便官方没做网页端）。
3. 结论输出：网页端能否读消息？若否 → **路线 C 判死**，转向 B 或 D。

---

### 问题 2 —「iOS 快捷指令能不能截 Bubble 的图？」（决定路线 B 成不成立）
**为什么关键**：若 iOS 能正常截到聊天内容（不被涂黑），就能用「快捷指令自动翻页 + 截图 + OCR」做半自动导出，绕开无网页端的问题。

**初步结论：⚠️ 技术上 iOS 大概率截得到，但需实机确认是否被涂黑/警告。**
- 关键技术事实：**Android 用 `FLAG_SECURE` 能真正禁止截图；iOS 没有等价的系统级 API**，App 无法真正阻止系统截图，只能：
  - (a) 用 secure text field / `UIScreen.isCaptured` 把敏感视图**涂黑**，或
  - (b) 监听 `userDidTakeScreenshot` 事件后**弹警告**。
- 因此常见现象是：**同一个 App，安卓截图被拦，iPhone 却能截**（这也是为什么 iPhone 粉丝能分享 bubble 私信截图）。bubble 2021 上线的「截图禁用」很可能是 Android 侧为主。

**code 需要验证（需真机 / 模拟器）**：
1. iOS 上手动截图 bubble 聊天页 → 内容是否正常显示、被涂黑、还是弹警告？
2. iOS 快捷指令 / 自动化（`Take Screenshot` action 或录屏帧提取）能否拿到聊天内容？
3. 若可行，评估 OCR 准确率（韩文 + emoji + 时间戳）与自动翻页方案（滚动/坐标点击）。
4. 结论输出：iOS 截图是否可用？→ 决定 B 是否作为主力或兜底方案。

---

### 问题 3 —「Bubble 有没有 GDPR/PIPA 数据导出入口？」（决定路线 A 成不成立）
**为什么关键**：韩国平台受《个人信息保护法》(PIPA) 约束，理论上必须响应「个人信息查阅请求」；若存在官方导出且**含消息正文**，这是最干净、零风险的路径。

**初步结论：⚠️ 有官方「查阅请求」通道，但导出是否包含聊天正文高度存疑。**
- 已确认：DearU 隐私政策写明依 **PIPA 第 35 条**可提出个人信息**열람청구（查阅请求）**，方式为书面/电子邮件；App 内 `[내 프로필]` 可查看/修改本人信息；并有更正/删除权。
- ⚠️ 重要坑：PIPA/GDPR 的「个人信息」通常指**账号/身份类数据**。偶像发给粉丝的**消息正文，法律上可能被视作平台/艺人一侧的内容**，未必落在「你的个人信息」导出范围内 → **官方导出很可能拿不到聊天记录本身**。
- 韩国公司默认适用 **PIPA**，GDPR 仅在处理欧盟居民数据时适用。

**code 需要验证**：
1. 找到确切的查阅/导出请求入口（隐私政策里的 DPO / 客服邮箱，如 `help_stars@dear-u.co`）。
2. 明确请求范围话术：能否点名要「**본인 수신 메시지 내역 전체 / chat message history**」。
3. 判断（或建议先发一封测试请求）：官方导出**是否真的包含消息正文**，返回格式（CSV/JSON/PDF？）、周期（法定 10 日内）。
4. 结论输出：A 能否拿到聊天正文？→ 若能，A 为首选；若只给账号信息，A 降级为「补充证据」，主力回到 B。

## 附录 A：问题2 —— iOS 截图/录屏验证 + 半自动导出方案

**重要纠偏**：iOS 的「快捷指令(Shortcuts)」**没有**能对任意第三方 App 前台画面截图的动作；`Take Screenshot` 类动作不适用于 bubble。因此 iOS 侧的可行实现是**屏幕录制 → 抽帧 → OCR**，而非「快捷指令自动截图」。

**Step 1 · 30 秒实机判定（本人做）** 🧑‍💻
1. 打开 bubble 某个聊天页 → 按「电源+音量↑」截图 → 看相册：**正常 / 全黑 / 没反应**？
2. 再从「控制中心」开一段**屏幕录制**，录 5 秒聊天页 → 回看录像：内容**正常 / 被涂黑**？
- 正常 → 路线 B 成立，进 Step 2。
- 涂黑 → iOS 侧也做了保护，B 降级（只能外部相机拍屏，成本高、质量差）。

**Step 2 · 半自动导出流水线（B 成立时）**
1. **采集**：系统屏幕录制；翻历史用 AssistiveTouch 自定义手势匀速上滑，或手动慢滑，保证每屏有重叠。
2. **抽帧**：`ffmpeg -i rec.mp4 -vf "fps=2,mpdecimate" frames/%04d.png`（去重、降帧）。
3. **OCR（韩文）**：优先 Apple 实况文本/Vision（内置、韩文准）；离线批处理可用 PaddleOCR / Tesseract `kor`。
4. **后处理**：按气泡/时间戳切分 → 跨帧去重合并 → 输出 JSON / Markdown 时间线。
- ⚠️ 长截图（滚动截屏）在 bubble 内多半不支持，别指望一张长图。

## 附录 C：路线 D —— App API 抓包发现 playbook（本人操作 🧑‍💻）

**目标**：确认 bubble App 是否用 REST/JSON 拉消息；若是，抓到这 4 样发我，我就能把 `scripts/bubble_pull.py` 补成一键翻页拉全量 → JSON：
1. 消息列表**请求方法 + 完整 URL**（含 query 参数）
2. **鉴权方式**（`Authorization: Bearer …` / Cookie / 自定义 header）
3. **分页参数**（cursor / page / `before_id` / timestamp 等）
4. **一条完整响应 JSON**（可给内容脱敏，但请保留字段名与结构）

**红线（不变）**：仅本人账号、本人数据、个人存档；不公开再分发；不绕付费墙；不碰他人账号。本路线可能触碰 DearU 服务条款，本人已知悉并同意尝试，风险自负。

**工具**：`mitmproxy`（免费、可脚本化，推荐）或 Proxyman（iOS 友好）。以下是 mitmproxy 电脑中间人方案。

**步骤**
1. 电脑装：`pipx install mitmproxy`（或 `brew install mitmproxy`），运行 `mitmweb`（默认代理端口 8080，Web UI 8081）。
2. iPhone 与电脑连**同一 WiFi**；iPhone → 设置 → WiFi → (当前网络) → 配置代理 → 手动 → 服务器填电脑局域网 IP、端口 `8080`。
3. iPhone Safari 打开 `mitm.it` → 下载 iOS 证书 → 设置 → 通用 → VPN与设备管理 里安装描述文件 → 再到 通用 → 关于本机 → 证书信任设置 → 对 mitmproxy 打开**完全信任**。
4. ⚠️ **SSL Pinning 判定**：打开 bubble，若 App 能正常联网 → 没做强 pinning，继续；若 bubble **一直转圈/报网络错**而其他 App 正常 → 很可能做了证书固定，普通 MITM 到此为止（绕过需脱壳/Frida，成本高）→ **判 D 受阻，回退 B**。
5. 正常的话：进一个聊天 → 上滑翻历史 → 在 mitmweb 里筛 host = `ba-api.dear-u.co`（或相近域名）的请求，找**响应里含消息文本/发送时间的那条**。
6. 按上面「目标」的 4 点记录并发我。（`scripts/bubble_pull.py` 已留好占位，等你的接口细节。）

**如果做了 SSL Pinning**：不强攻。回退到附录 A 的**录屏 + 抽帧 + 韩文 OCR**，那条不依赖网络层、100% 可行，只是要 OCR 后处理。
